# shimeji-desktop — spec de design

Date : 2026-09-08
État : validée section par section, prête pour le plan d'implémentation

Ce document est le design complet. `CLAUDE.md` en est le résumé durable ; en cas de
divergence, ce document fait référence pour le *pourquoi*, `CLAUDE.md` pour le *quoi*.

---

## 1. Objet

Un *desktop pet* Windows : des personnages en pixel-art vivent sur le bureau, grimpent
sur les bords des fenêtres ouvertes, et réagissent à l'activité de la machine. Les packs
de personnages **Shimeji** existants fonctionnent tels quels.

Le besoin fonctionnel complet et les hors-sujets sont dans `CLAUDE.md`. Cette spec
traite le *comment*.

### Critère de réussite

Il n'est pas fonctionnel, il est subjectif : **on a envie de le regarder au bout d'une
semaine**. Tout arbitrage se tranche par « est-ce que ça le rend plus vivant ? », pas
par « est-ce que c'est plus correct ? ». Deux conséquences assumées plus loin : les
signaux biaisent au lieu de commander (§7.2), et la navigation a le droit d'être bête
(§7.3).

---

## 2. Les cinq décisions structurantes

Chacune supprime une classe entière de bugs. Elles sont reprises dans `CLAUDE.md` sous
« décisions à ne pas défaire ». Le raisonnement complet est ici.

| # | Décision | Classe de bugs supprimée |
|---|---|---|
| 1 | Position **dérivée**, jamais stockée (§6.2) | tout le comportement des fenêtres qui bougent, se redimensionnent, se ferment |
| 2 | Premier plan **+** bords recouverts exclus (§5.4) | se tenir sur un bord invisible |
| 3 | Les signaux **biaisent**, ne commandent pas (§7.2) | le personnage prévisible, donc abandonné |
| 4 | La navigation a le **droit d'échouer** (§7.3) | tous les blocages, sans les énumérer |
| 5 | Le comportement est de la **donnée** (§7.1) | un nouveau chemin de code par signal ajouté |

## 3. Architecture

### 3.1 Répartition

| Couche | Où | Contenu |
|---|---|---|
| Système | Rust | fenêtres, signaux, tray, config, persistance |
| Simulation | Rust | physique, accroches, intentions, envies, social |
| Rendu | Webview | recevoir une frame, l'afficher. Rien d'autre. |

Le webview est **délibérément bête** : il reçoit `{ image, flip }` et pose un
`background-image`. Aucune décision, aucun état, aucune horloge.

**Pourquoi la logique n'est pas en JS.** La position est appliquée par Rust
(`set_position`). Si la physique vivait en JS, chaque image coûterait un aller-retour
IPC pour rapatrier une position que Rust doit de toute façon appliquer — 60 fois par
seconde, par personnage. Corollaire heureux : Rust détenant *tous* les personnages, le
comportement social (§7.4) est une simple vérification locale, sans canal inter-fenêtres
à inventer.

### 3.2 Une fenêtre par personnage

Chaque personnage est sa propre fenêtre : `128×128`, transparente, sans décoration,
non focalisable, hors taskbar, sans ombre, toujours au premier plan.

**Rejeté : l'overlay transparent plein écran.** Une fenêtre unique ne peut pas couvrir
proprement deux moniteurs de DPI différents — c'est structurel, pas contournable. Elle
impose aussi une couche always-on-top au-dessus de tout le bureau (coût de composition,
conflits avec le plein écran exclusif des jeux). Avec une fenêtre par personnage,
changer d'écran, c'est écrire une position.

### 3.3 Hit-testing

Les clics traversent en permanence (`set_ignore_cursor_events(true)`). Rust sonde
`GetCursorPos` à ~30 Hz — quasi gratuit — et ne réactive les événements que quand le
curseur entre dans la **hitbox** déclarée par la pose courante (§8.4). En sortie, on
repasse à `true`.

Sans ça, la boîte de 128×128 attraperait les clics dans ses zones transparentes, et le
personnage deviendrait un trou noir de 128 px sur le bureau.

### 3.4 Coordonnées

**Tout est en pixels physiques du bureau virtuel**, sans exception. Le facteur d'échelle
d'un moniteur ne sert qu'à dimensionner le sprite à l'affichage (§8.5). Mélanger
coordonnées logiques et physiques sur une machine multi-DPI produit des décalages qui ne
se reproduisent que sur un écran, et c'est un enfer à diagnostiquer.

## 4. Prérequis et distribution

- **Compilation** : Rust (MSVC), composants C++ de Visual Studio, `cargo-tauri`.
- **Pas de Node.** On passe par `cargo-tauri`, pas par le CLI npm. Le front est statique :
  aucun bundler, aucun `package.json`. (La voie npm exigerait Node 18+ ; s'en passer
  supprime la contrainte.)
- **Exécution** : WebView2 (présent d'origine sur Windows 11) + runtime Visual C++, ce
  dernier **lié statiquement** pour que l'exe soit autonome.
- **Livraison** : un dossier — l'exe, `characters/`, `config.json`. Zippable tel quel.
- Un exe non signé déclenche SmartScreen (« Informations complémentaires » → « Exécuter
  quand même »). Acceptable pour un usage privé ; un certificat coûte ~200 €/an.

## 5. Le monde

### 5.1 Plateformes

Tout ce sur quoi un personnage peut se tenir, s'accrocher ou se suspendre est une
**plateforme** : un rectangle, plus les faces utilisables.

```rust
struct Platform {
    id:   PlatformId,     // stable dans le temps — dérivé du handle de fenêtre ou de l'écran
    rect: Rect,           // pixels physiques du bureau virtuel
    kind: PlatformKind,   // Screen | Window
    z:    u32,            // 0 = au-dessus de tout
}

enum Face { Top, Left, Right, Bottom }
```

Deux sources, et deux seulement :

| Source | Faces |
|---|---|
| chaque écran | `Top` = **zone de travail** (pas l'écran, sinon il marche sous la taskbar), `Left`/`Right` = bords, `Bottom` = plafond |
| chaque fenêtre retenue | `Top` = barre de titre, `Left`/`Right` = bords, `Bottom` = dessous (suspension) |

**La physique et les comportements ne savent jamais laquelle des deux ils manipulent.**
C'est ce qui permet de livrer l'étape 1 (sol seul, une plateforme) et de brancher
l'étape 4 (fenêtres, N plateformes) sans toucher ni la physique ni le comportement.

### 5.2 Identité stable

`PlatformId` dérive du handle de fenêtre. « La plateforme sur laquelle je suis » survit
donc au déplacement et au redimensionnement de la fenêtre. C'est la condition qui rend
la décision n° 1 (§6.2) possible.

### 5.3 Filtrage des fenêtres

Sont **exclues** :

- les fenêtres non visibles et les minimisées ;
- les fenêtres **masquées** (`DWMWA_CLOAKED`) — Windows 11 en est plein : des applis
  modernes déclarent des fenêtres invisibles qui se présentent comme visibles. Sans ce
  filtre, le personnage s'assoit sur des rectangles qui n'existent pas à l'écran ;
- les fenêtres outils (`WS_EX_TOOLWINDOW`) et sans activation ;
- les fenêtres trop petites pour être praticables ;
- le bureau et la barre des tâches ;
- **les fenêtres des personnages eux-mêmes** — sans quoi ils s'assoient les uns sur les
  autres, et un personnage se poursuit lui-même.

**Le rectangle utilisé n'est pas celui que Windows rapporte.** `GetWindowRect` inclut
~7 px de bordure de redimensionnement invisible de chaque côté sur Win10/11. Utilisé tel
quel, le personnage flotte 7 px au-dessus de la barre de titre : subtilement faux, et
très visible sur du pixel-art. On demande les bornes **visuelles** au compositeur —
`DwmGetWindowAttribute` / `DWMWA_EXTENDED_FRAME_BOUNDS`.

### 5.4 Occlusion — décision n° 2

Le personnage reste **toujours au premier plan** (c'est un animal de compagnie : on veut
le voir). En échange, **un bord recouvert n'est jamais exposé comme plateforme.**

Un bord est un segment. On lui retire les fenêtres de z-order supérieur : de la
soustraction d'intervalles en 1D, pas de la géométrie.

```
bord haut d'une fenêtre   ├────────────────────────────┤
fenêtre au-dessus                    ▓▓▓▓▓▓▓▓▓▓▓
                                     ↓
plateformes exposées      ├────────┤           ├───────┤
```

Il devient alors **physiquement incapable** de se tenir sur du vide — plutôt que d'avoir
à détecter puis corriger le cas.

### 5.5 Les trois horloges

| Rythme | Quoi | Justification |
|---|---|---|
| **60 Hz** | physique, rendu, **et la seule plateforme occupée** | interroger *une* fenêtre est quasi gratuit → il colle parfaitement à la fenêtre qu'on déplace |
| **~8 Hz** | recensement complet, filtrage, occlusion | une fenêtre qui apparaît est vue en ~125 ms : imperceptible |
| **~2 Hz** | inactivité, appli active, heure, batterie | aucun de ces signaux ne bouge vite |

Le suivi ciblé à 60 Hz de la seule plateforme occupée est ce qui évite l'arbitrage
« recenser tout à 60 Hz » (gaspillage) contre « recenser à 8 Hz » (le personnage traîne
derrière la fenêtre qu'on déplace).

## 6. Le personnage

### 6.1 État

```rust
struct Character {
    manifest:   Manifest,
    attachment: Attachment,
    facing:     Facing,        // Left | Right
    pose:       PoseId,
    frame:      usize,
    intention:  Option<Intention>,
}

enum Attachment {
    On { platform: PlatformId, face: Face, offset: f32 },  // offset le long de la face
    Falling { vel: Vec2, pos: Point },                     // seul cas avec position absolue
    Dragged,
}
```

### 6.2 Position dérivée — décision n° 1

> **Un personnage accroché ne stocke jamais sa position absolue.**

Il stocke `(plateforme, face, offset)`. Sa position écran est **recalculée à chaque
image** depuis le rectangle courant de la plateforme, puis l'ancre de la pose (§8.3) est
posée dessus.

Ce que cette seule décision rend gratuit :

| Événement | Code nécessaire |
|---|---|
| la fenêtre est déplacée | **aucun** — il voyage avec elle |
| la fenêtre est redimensionnée | **aucun** — il garde son offset |
| elle rétrécit sous lui | un test : `offset > longueur de face` → `Falling` |
| elle se ferme / se minimise | un test : plateforme absente → `Falling` |

Un personnage assis sur une barre de titre qu'on balade est *le* moment qui fait sourire
avec un Shimeji. Ici, c'est une conséquence du modèle, pas une fonctionnalité à écrire.

`Falling` est le seul état à position absolue — c'est cohérent : en chute, il n'est
attaché à rien.

### 6.3 Transitions

Évaluées à chaque image, avant toute décision de comportement :

| Depuis | Événement | Vers |
|---|---|---|
| `On` | plateforme absente ou offset hors bornes | `Falling` |
| `On` | bout de la face atteint | demi-tour · `Falling` · accroche à une face voisine (tirage) |
| `On` | pression souris dans la hitbox | `Dragged` |
| `Falling` | intersection avec une face `Top` | `On` (pose d'atterrissage) |
| `Falling` | sous le bas du bureau virtuel | replacé sur le sol de l'écran le plus proche |
| `Dragged` | relâchement | `Falling` |

Le dernier garde-fou de `Falling` évite la perte définitive d'un personnage lâché hors
écran.

## 7. Le comportement

### 7.1 Trois couches — décision n° 5

Elles ne communiquent que vers le bas.

```
                 chaque image (60 Hz)
                         │
                         ▼
   ┌──────────────────────────────────────────────┐
   │  1. RÉFLEXES — non négociables               │
   │     plateforme disparue   → je tombe         │
   │     attrapé à la souris   → je suis porté    │
   │     contact avec le sol   → j'atterris       │
   │     session verrouillée   → je disparais     │
   └──────────────────────────────────────────────┘
                         │ rien ne s'est imposé
                         ▼
   ┌──────────────────────────────────────────────┐
   │  2. INTENTION en cours — une seule à la fois │
   │     Flâner  ·  AllerÀ(surface)               │
   │     SeReposer  ·  Jouer(action)              │
   │     → traduite en déplacement + pose         │
   └──────────────────────────────────────────────┘
                         │ finie · échouée · expirée
                         ▼
   ┌──────────────────────────────────────────────┐
   │  3. ENVIE — tirage pondéré                   │
   │     signaux ────────► modifient les poids    │
   │     slots manquants ─► retirent les options  │
   └──────────────────────────────────────────────┘
```

Les réflexes ne sont pas des décisions, ce sont des conséquences physiques : ils ne
consultent ni l'envie ni l'intention.

### 7.2 Les signaux biaisent — décision n° 3

> Si « inactif 2 min » **déclenchait** le sommeil, on aurait un afficheur d'état système
> déguisé en personnage : parfaitement prévisible, abandonné en trois jours. « Inactif
> 2 min » **multiplie par 8 l'envie de dormir** : il s'endort presque toujours, mais
> parfois il s'assoit, parfois il traîne encore un peu. **Cette marge est le produit.**

Table d'envies (valeurs de départ, à régler à l'usage) :

| Intention | Base | Modificateurs |
|---|---|---|
| Flâner | 5 | × 0,2 si inactif > 2 min |
| Se reposer / dormir | 1 | **× 8** si inactif > 2 min · × 3 le soir |
| Manger | 1 | **× 6** entre 12 h et 14 h |
| Aller à la fenêtre active | 2 | × 4 si l'appli active vient de changer |
| Aller voir l'autre personnage | 1 | × 3 s'il est proche |
| S'amuser | 1 | × 3 selon l'appli active |

Signaux disponibles : inactivité, appli au premier plan, heure, batterie, verrouillage
de session. **Pas la charge CPU** — écartée explicitement.

Modificateurs par application, éditables par l'utilisateur :

```
Code.exe    → s'amuser ×3,   flâner ×0,5
chrome.exe  → se reposer ×2, flâner ×1,5
```

Trois propriétés qui découlent de cette forme :

- ajouter un signal = **ajouter une ligne**, aucun nouveau chemin de code ;
- un personnage à couverture partielle (§8.6) fonctionne sans cas particulier — l'option
  est simplement retirée du tirage ;
- les poids étant de la donnée, on **règle son caractère sans recompiler**.

### 7.3 Navigation — décision n° 4

**Aucun calcul de chemin.** La carte des plateformes change 8 fois par seconde : un
chemin calculé est périmé avant d'être parcouru, et le maintenir à jour coûterait plus
que le bénéfice.

Décision **locale** à chaque image :

| Situation | Prochain pas |
|---|---|
| la cible est sur ma surface | avancer vers elle |
| elle est au-dessus | chercher une paroi escaladable de ce côté ; adjacente → grimper ; sinon s'en approcher |
| elle est en dessous | aller au bord le plus proche et se laisser tomber |
| sa surface a disparu | l'intention échoue |

Ça échoue parfois : il se coince dans un coin, il prend une route absurde. **C'est
souhaitable** — un pet qui prend un chemin bête est attachant, un qui calcule
l'itinéraire optimal a l'air d'un robot. Le critère de réussite (§1) tranche en faveur
de la bêtise.

Une seule règle remplace toute l'énumération des cas de blocage :

> **Toute intention a un délai d'abandon (~20 s).** Passé ce délai, elle échoue et il
> repart flâner.

On ne cherche donc jamais à recenser les situations de blocage : on rend le blocage
temporaire par construction. C'est le pendant de la décision n° 1 — là on rendait les
fenêtres mobiles gratuites, ici on rend les échecs de navigation inoffensifs.

### 7.4 Social

Volontairement minimal :

- une intention **« aller voir l'autre »**, dont le poids monte avec la proximité ;
- sur la même surface et à faible distance → une **rencontre** : chacun joue une
  réaction ;
- un **temps de repos** ensuite, sans quoi ils bouclent.

Rust détenant tous les personnages (§3.1), une rencontre est une vérification côté
coordinateur : aucun protocole de négociation.

**Hors sujet :** système de relations, humeur partagée, amitié qui évolue. Une intention,
une interaction. Le reste s'ajouterait comme des lignes dans la table.

## 8. Format de personnage

### 8.1 Externe, jamais embarqué

```
shimeji-desktop.exe
config.json
characters/
└── blob/
    ├── mascot.json
    └── img/
        └── shime1.png … shime46.png
```

Trois raisons : ajouter un personnage sans recompiler, itérer sur les animations sans
build, et permettre à quelqu'un d'autre de déposer le sien sans rien connaître au projet.

Résolution des chemins : **à côté de l'exe d'abord** (mode portable), repli sur
`%APPDATA%\shimeji-desktop\` si le dossier n'est pas inscriptible.

### 8.2 Le vocabulaire = les slots Shimeji

La numérotation `shime1..46` est un **standard de fait** : tous les packs Shimeji
utilisent les mêmes numéros pour les mêmes poses, parce qu'ils sont tous dessinés contre
la même configuration d'origine. En visant ce vocabulaire, **tout pack trouvé sur
internet fonctionne avec nos comportements, sans code.**

**On ne lit que les images**, par leur numérotation. On **n'implémente pas** les
`actions.xml` / `behaviors.xml` : séquences imbriquées, sélecteurs conditionnels et
expressions Java évaluées à l'exécution en font un projet à part entière, et cela
enfermerait le design dans la sémantique du Shimeji Java — où nos signaux système
n'existent pas.

### 8.3 Une frame = un fichier + une ancre

Toutes les frames sont en `128×128`, le personnage placé dans la boîte. Chaque pose
déclare une **ancre** : le point du sprite à faire coïncider avec sa position sur la
plateforme.

L'ancre dépend de la pose, et c'est tout l'intérêt :

| Pose | Ancre |
|---|---|
| debout, marche | le sol sous les pieds — bas, centré |
| accroché à une paroi | la main qui agrippe — sur le côté |
| suspendu au plafond | les mains — en haut |

> **Ne jamais recalculer une compensation de décalage quand la taille du sprite change.**
> L'ancre existe exactement pour rendre ce contournement inutile. Le prototype VSCode
> (`../op`) en contenait un, asymétrique selon le sens de marche ; il disparaît ici.

### 8.4 Hitbox

Chaque pose déclare une **hitbox serrée** — le rectangle réellement occupé par le
personnage dans la boîte de 128×128. Elle sert au hit-testing (§3.3) et à la détection
de proximité entre personnages (§7.4).

### 8.5 Manifeste

```json
{
  "id": "blob",
  "name": "Shimeji (mascotte par défaut)",
  "frameSize": [128, 128],
  "scale": 1,
  "poses": {
    "stand":     { "frames": [1],            "anchor": [64, 120] },
    "walk":      { "frames": [2, 3, 1, 4],   "frameMs": 120, "loop": true },
    "run":       { "frames": [30, 31, 32, 33], "frameMs": 80, "loop": true },
    "sit":       { "frames": [39] },
    "sleep":     { "frames": [39, 40, 41],   "frameMs": 400, "hold": 41 },
    "fall":      { "frames": [10],           "anchor": [64, 64] },
    "land":      { "frames": [4],            "frameMs": 150 },
    "crawl":     { "frames": [18, 20, 21],   "frameMs": 200, "loop": true },
    "cling":     { "frames": [23, 24, 25],   "frameMs": 150, "loop": true, "anchor": [110, 64] },
    "climbOver": { "frames": [34, 35, 36],   "frameMs": 180 },
    "hang":      { "frames": [22],           "anchor": [64, 10] },
    "dragged":   { "frames": [10] },
    "split":     { "frames": [44, 45, 46],   "frameMs": 200 }
  },
  "hitbox": [40, 20, 48, 100]
}
```

Sémantique des champs, pour lever toute lecture double :

| Champ | Signification | Défaut |
|---|---|---|
| `frames` | numéros de `shime<n>.png`, dans l'ordre de lecture | obligatoire |
| `frameMs` | durée d'affichage d'une frame | 150 |
| `loop` | rejouer indéfiniment | `false` |
| `hold` | frame conservée à l'arrêt quand `loop` est faux — c'est ce qui permet de *rester* endormi après la séquence d'endormissement | dernière frame |
| `anchor` | `[x, y]` dans la boîte de 128×128 | `[64, 120]` (sol, centré) |
| `hitbox` | `[x, y, largeur, hauteur]` dans la boîte, au niveau du personnage ; surchargeable par pose | obligatoire |

`scale` multiplie la taille d'affichage ; le facteur d'échelle du moniteur s'y combine
(§3.4). L'orientation est obtenue par miroir horizontal — pas de frames dédiées.

**La correspondance frames → poses ci-dessus est un point de départ**, établi à l'œil sur
`blob`. La raffiner consiste à éditer du JSON : c'est précisément le bénéfice du format.

### 8.6 Couverture partielle

Un personnage sans images d'escalade **ne grimpera jamais** : l'intention est retirée du
tirage (§7.2). Aucun cas particulier, aucune erreur. C'est ce qui rend utilisables les
packs tiers incomplets, et c'est aussi ce qui permettrait d'ajouter un personnage dessiné
soi-même n'ayant que quelques poses.

### 8.7 Le personnage de test — `blob`

Mascotte blanche par défaut de Shimeji-ee, 46 frames de 128×128. Elle possède **toutes**
les poses, y compris celles qui débloquent les comportements difficiles.

| Frames | Pose |
|---|---|
| 23, 24, 25 | agripper une paroi verticale (**escalade**) |
| 34, 35, 36 | se hisser par-dessus un bord |
| 22 | suspension au plafond |
| 39, 40, 41 | s'asseoir puis dormir |
| 10 / 4 | chute / atterrissage |
| 18, 20, 21 | ramper |
| 44, 45, 46 | dédoublement |

Développer contre `blob` **découple « le moteur fonctionne » de « j'ai les bons
dessins »** — c'était le risque de contenu principal du projet, et il tombe.

> L'art de cette mascotte n'est pas de nous. Sans conséquence en usage privé ; à vérifier
> avant toute publication du dépôt.

## 9. Tour du propriétaire

### 9.1 Tray

Afficher/cacher · ajouter un personnage · en retirer un · ouvrir le dossier des
personnages · **recharger les personnages** · démarrer avec Windows · quitter.

Le **rechargement à chaud** pèse plus qu'il n'y paraît : c'est lui qui rend supportable
le réglage des animations. Sans lui, chaque ajustement de timing coûte un redémarrage, et
le réglage du manifeste — qui sera l'essentiel du travail de finition — devient pénible.

### 9.2 Démarrage automatique

Case à cocher dans le tray, écrite dans la clé `Run` de l'utilisateur courant. Au
démarrage automatique : **aucune fenêtre, aucune notification, aucun vol de focus.**

### 9.3 Config

Un `config.json`, résolu comme les personnages (§8.1) : à côté de l'exe, sinon
`%APPDATA%`. Contenu : personnages à instancier, échelle, vitesse, table d'envies,
modificateurs par application, démarrage automatique.

Toutes les valeurs ont un défaut dans le code : **l'absence de fichier n'est pas une
erreur**, et un fichier partiel ne l'est pas davantage.

## 10. Stratégie de vérification

L'intuition est fausse : un programme visuel et aléatoire *paraît* intestable. En
réalité, presque tout le cœur est une fonction pure.

### 10.1 Testable sans écran

| Sujet | Nature du test |
|---|---|
| Soustraction d'intervalles (§5.4) | un segment + N rectangles → sous-segments attendus |
| Filtrage des fenêtres (§5.3) | fenêtres factices → celles retenues |
| Position dérivée (§6.2) | on déplace le rectangle → la position suit |
| Transitions d'accroche (§6.3) | plateforme retirée → `Falling` ; rétrécie → `Falling` |
| Chute | intégration déterministe : hauteur et durée connues |
| Tirage pondéré (§7.2) | 10 000 tirages à graine fixe → distribution attendue |
| Couverture partielle (§8.6) | manifeste amputé → l'intention n'est jamais tirée |
| Délai d'abandon (§7.3) | horloge injectée → échec à 20 s |
| Manifeste malformé | erreur explicite, aucune panique |
| Ancres (§8.3) | pose donnée + position → coordonnées de fenêtre attendues |

### 10.2 Trois contraintes de conception imposées par les tests

Elles doivent être en place **dès le départ** ; elles ne se rattrapent pas après.

1. **Le temps est injecté**, jamais lu depuis l'horloge système → sans quoi rien de
   temporel n'est testable.
2. **L'aléatoire est injecté et graînable** → sans quoi rien de pondéré n'est testable.
3. **La couche win32 est derrière une interface** → sans quoi aucun test ne peut fournir
   de fausses fenêtres.

Ce sont les tests qui dictent ces trois choix, et non l'inverse — d'où leur place dans le
design plutôt que dans le plan.

### 10.3 Mode simulation

Un mode sans écran qui déroule N minutes de comportement contre un monde factice à graine
fixe, et imprime la trace des intentions et des poses.

Permet de vérifier « il a dormi, mangé, flâné, jamais bloqué plus de 20 s » sans regarder
l'écran, et rend les **régressions de comportement** détectables — ce qu'aucun test
unitaire ne couvre.

### 10.4 Ce qui reste à l'œil humain

- que la transparence, le premier plan et les clics traversants fonctionnent (**le spike**) ;
- qu'il soit joliment posé sur une barre de titre ;
- qu'il ait l'air vivant, sur plusieurs jours.

Rien d'autre.

## 11. Étapes de livraison

Chaque étape est agréable en elle-même, et aucune ne dépend d'un dessin manquant.

| | Étape | Résultat |
|---|---|---|
| 0 | **Spike jetable** | fenêtre transparente, sans bordure, premier plan, hors taskbar, clics traversants, PNG déplacé à 60 Hz, sur deux écrans de DPI différents |
| 1 | **Il vit sur le sol** | marche, court, s'arrête, demi-tour ; tous les écrans ; attrapable, il tombe et atterrit ; tray, démarrage auto, config |
| 2 | **Il réagit** | s'endort à l'absence, se réveille au retour, mange à midi |
| 3 | **Un deuxième personnage** | coexistence et rencontres |
| 4 | **Il grimpe** | plateformes de fenêtres, escalade, barres de titre, chute à la fermeture |
| 5 | **Il suit** | navigation vers l'application au premier plan |

**L'étape 0 est non négociable.** Le seul point faible de Tauri face à Electron est
justement l'overlay transparent : il faut le prouver sur la machine cible avant d'écrire
une ligne de physique, pas après. Le code du spike est jetable par définition — son
produit est une réponse.

À l'étape 1, le monde n'expose **qu'une plateforme par écran** (le sol). L'étape 4 se
contente d'en ajouter : ni la physique ni le comportement ne changent. C'est le
dividende du §5.1.

## 12. Risques

| Risque | Gravité | Traitement |
|---|---|---|
| La transparence Tauri se comporte mal sur cette machine | **haute** | étape 0 avant tout le reste ; repli documenté sur Electron, le design restant valable à 90 % |
| Rust est à apprendre en même temps que le projet | moyenne | étapes courtes et agréables ; le win32 typé évite la classe de bugs la plus punitive |
| Déplacer une fenêtre à 60 Hz saccade | moyenne | mesuré à l'étape 0 ; repli : 30 Hz avec interpolation |
| Recensement des fenêtres trop coûteux | faible | ~8 Hz, et suivi ciblé de la seule plateforme occupée (§5.5) |
| Le personnage n'a pas l'air vivant | moyenne | c'est le critère de réussite (§1) ; le mode simulation (§10.3) permet d'itérer sur les poids sans attendre |
| Licence de l'art de `blob` | faible | usage privé ; à traiter avant publication |

## 13. Écarté explicitement

| Rejeté | Raison |
|---|---|
| Overlay transparent plein écran | ne couvre pas proprement deux moniteurs de DPI différents (§3.2) |
| Physique et comportement en JS | 60 allers-retours IPC par seconde et par personnage (§3.1) |
| Lire les XML Shimeji | projet à part entière, et enferme le design dans la sémantique Java (§8.2) |
| Calcul de chemin | la carte change 8 fois par seconde (§7.3) |
| Charge CPU comme signal | écartée par l'utilisateur |
| Hook clavier global | signature de keylogger, faux positifs antivirus ; l'inactivité suffit |
| Stats persistantes (Tamagotchi) | ajoute une obligation — hors sujet (`CLAUDE.md`) |
| TypeScript, bundler, framework front, canvas | le webview affiche un sprite ; aucun de ces outils ne sert |
| Système de relations entre personnages | une intention et une interaction suffisent (§7.4) |
